Roadmap

처음부터 실무까지 가는 순서

아래 순서는 프론트엔드, 백엔드, 앱, 데이터 분야 모두에 공통으로 필요한 기반을 먼저 쌓도록 설계했습니다.

01

컴퓨터 기본기

자료구조, 알고리즘, 운영체제, 네트워크, HTTP, 프로세스와 스레드 개념을 말로 설명할 수 있어야 합니다.

02

언어와 런타임

주력 언어의 타입, 메모리, 비동기 처리, 에러 처리, 패키지 생태계를 작은 프로젝트로 검증합니다.

03

웹과 데이터

브라우저, API, 인증, SQL, 인덱스, 캐시, 배포 환경을 연결해 하나의 서비스 흐름으로 이해합니다.

04

품질과 운영

테스트, 로깅, 모니터링, 장애 대응, 코드 리뷰 기준을 익혀 만든 기능이 운영 가능한 상태인지 판단합니다.

Skills

개발자가 갖춰야 하는 역량

기술 스택보다 오래가는 역량을 중심으로 분류했습니다. 검색으로 필요한 항목만 빠르게 좁혀볼 수 있습니다.

01

문제 해결력

현상을 재현하고, 가설을 세우고, 로그와 데이터로 원인을 좁히는 능력입니다.

02

코드 품질

읽기 쉬운 이름, 작은 함수, 명확한 책임, 테스트 가능한 구조로 변경 비용을 낮춥니다.

03

시스템 사고

요청이 들어와 저장되고 응답되는 전체 경로에서 병목과 실패 지점을 예상합니다.

04

데이터 감각

스키마, 인덱스, 트랜잭션, 정합성, 캐시 무효화를 서비스 요구사항과 연결합니다.

05

협업 능력

결정 배경을 문서화하고, 리뷰 가능한 단위로 작업하며, 모호한 요구사항을 질문으로 정리합니다.

06

보안 기본기

인증과 인가, 입력 검증, 비밀 값 관리, 개인정보 처리 기준을 기본 설계에 포함합니다.

Interview

면접에서 자주 확인하는 기준

답을 외우기보다 자신의 프로젝트 경험과 연결해 설명할 수 있어야 합니다.

기술 선택을 어떻게 설명할 것인가?

사용한 기술의 장점뿐 아니라 포기한 선택지, 비용, 팀 상황, 운영 난이도까지 같이 말해야 설득력이 생깁니다.

버그를 어떻게 추적했는가?

재현 조건, 관찰한 로그, 세운 가설, 틀린 가설, 최종 원인, 재발 방지책 순서로 정리하면 좋습니다.

성능 개선 경험을 어떻게 말할 것인가?

측정 지표, 병목 위치, 적용한 변경, 개선 수치, 부작용 여부를 함께 제시해야 합니다.

협업 충돌은 어떻게 풀었는가?

감정이 아니라 기준을 세우고, 요구사항과 제약을 분리하고, 기록으로 합의한 경험을 설명합니다.
